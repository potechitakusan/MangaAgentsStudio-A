# 生成AIで漫画を制作するための共通知識

確認日: 2026-09-12（NovelAI Opusの生成条件は2026-09-20に追加確認）。対象: キャラクターの見た目、表情・ポーズ、コマ間の絵柄を揃える制作工程。
公式資料に基づく機能の整理と制作実験の設計をまとめる。出典は末尾を参照。実行環境と生成結果は各作品の通常の制作記録へ残し、資料の確認と実機での動作確認を区別する。

## 1. 一貫性を何で判断するか

**制作上の提案:** 「同じキャラ」と「同じ絵柄」と「同じ構図」を別々に採点する。顔が似ていても衣装が変われば連続性は崩れ、同じポーズばかりでは芝居が成立しない。

| 軸 | 固定したいもの | シーンに応じて変えてよいもの |
| --- | --- | --- |
| キャラ同一性 | 顔の輪郭、目の形、前髪、髪の長さ、体格、識別用の小物 | 表情、視線、角度、動作 |
| 衣装の連続性 | 襟、袖、模様、留め具、左右非対称の印 | しわ、風や動作による変形、物語で指定した汚れ |
| 絵柄 | 線の太さ、描き込み量、陰影、黒ベタ、トーンの粒度 | 感情に応じたデフォルメ、演出として指定した密度 |
| 空間の連続性 | 身長差、持ち手、立ち位置、光源、背景の目印 | カメラ位置、画角、遠近 |

キャラ台帳では「必ず保持する特徴」5～8項目、衣装版、左右の目印、許容デフォルメを文字で定義する。画像の雰囲気だけで採否を決めない。顔が隠れるコマは同一性の該当項目を N/A とし、髪や衣装で判断する。

## 2. 手段と使いどころ

| 手段 | 公式資料で確認した範囲 | 制作上の採用案・未検証事項 |
| --- | --- | --- |
| 固定プロンプトとseed | NovelAIは設定変更の比較にseedを使えるが、同じseedでも服の指定変更で他の部分も変わり得る [A04] | まず比較条件を揃える。seedをキャラIDとして扱わない |
| キャラ参照画像 | NovelAI Precise Referenceは人物、絵柄、その両方を参照する機能。確認時はV4.5限定でVibe Transferと非互換 [A03] | 最初は単独人物で検証。複数キャラ参照の混合を二人の描き分けと取り違えない |
| Qwen画像編集 | 正式名は **Qwen-Image-Edit-2511**。開発元は人物同一性と複数人物の編集改善を報告 [A01] | 承認済みキャラシートから別角度・別ポーズへ編集する候補。漫画絵への効果は実測する |

## 3. キャラクターシート

NovelAI公式は、単純な背景でニュートラルな全身像、必要に応じて顔の拡大や多方向の参照を用意する方法を案内している。参考タグには `multiple views`、`turnaround`、`reference sheet`、`no text` がある。参照を強くし過ぎると角度や表情まで固定される場合がある。[Precise Reference](https://docs.novelai.net/en/image/precisereference/)（2026-09-12、NovelAI V4.5）

**制作上の提案:** 以下を作品側に置き、メインエージェントが採用版を一つ決める。

1. 基準の正面全身、斜め、横、後ろ。左右の小物の位置を目視で突き合わせる。
2. 同一キャラの顔の拡大、無表情・笑顔・驚きの比較。生成した別角度が矛盾する場合は基準として配らない。
3. 衣装と小物の詳細。色版があれば基準色、白黒版なら明度やトーン指定を記載する。
4. 参照画像の版番号・ハッシュ、採用日、変更理由。不採用画像を基準のフォルダへ混在させない。

一覧シートを参照すると細部が小さくなるため、顔アップのコマには顔参照、全身コマには全身参照も比較する。新しい生成を直前の生成から繰り返し編集するだけにせず、採用済みの基準に戻る工程を置き、累積変化を検出する。

## 4. Qwen-Image-Edit-2511の扱い

入力の `QwenImageEdit2511` は公式の **Qwen-Image-Edit-2511** に対応する。2509やQwenの他モデルへ自動的に読み替えない。公式モデルカードの「組み込みLoRA」は開発元が選んだ機能の統合を指し、制作キャラのLoRAを自動学習するという意味ではない。[公式モデルカード](https://huggingface.co/Qwen/Qwen-Image-Edit-2511)（2026-09-12、2511モデル）

ComfyUI公式の2511例は、拡散モデル、Qwenテキストエンコーダー、Qwen VAEを組み合わせ、任意で2511用4-step Lightning LoRAを利用する構成。公式例の拡散重みは `qwen_image_edit_2511_bf16.safetensors`。ローカルにあるFP8名のファイルを公式BF16例と同じ重み・品質とみなさない。[ComfyUI公式2511例](https://docs.comfy.org/tutorials/image/qwen/qwen-image-edit-2511)（2026-09-12、当該ワークフロー）

**実験案:** まず人物1名、参照1枚、編集指示1種類でワークフローが成立するかを確認する。次に顔参照と全身参照、最後に二人の描き分けを検証する。Lightning有無は別条件として比較し、通常版のstepsやguidanceを無条件で流用しない。FP8の配布元、モデルハッシュ、ノード対応、精度設定を確認した上で、時間・メモリ・採用率を測る。

## NovelAI OpusでAnlasを消費しない生成条件

**確認事実（2026-09-20）:** 公式の契約案内は、Opusの対象を1024×1024pxまで・28ステップ以下・１回１枚の生成としている。画像生成の説明は通常サイズ以下を条件とし、複数枚の同時生成はOpusでもAnlasを消費する。元画像を使うImage2Imageはこの基本無料条件に含めない。[契約条件](https://docs.novelai.net/en/subscription/)、[ステップ数](https://docs.novelai.net/en/image/stepsguidance/)、[画像生成・枚数設定](https://docs.novelai.net/en/image/)。ここでいう無料枠は有料のOpus契約中のAnlas消費なし特典であり、未契約の無料体験とは別。

1024×1024＝1,048,576画素という条件を「各辺1024px以下」と読み替えず、カスタム寸法は画素数の計算だけで無料と断定しない。生成寸法は共通の [ページ設定](page-layout.md)に従って使用ツールに合わせ、採用した寸法での費用を実行前に確認する。

**本キットの既定手順:** 使用する画像生成環境がNovelAIで、有効なOpus契約を確認できた場合だけ、次の条件を適用する。会話や確認済みの環境情報で分かっていれば同じ質問を繰り返さない。未確認のプランをOpusと仮定せず、他の生成環境にはこれらの条件を強制しない。

| 項目 | Opus利用時の初期設定 |
| --- | --- |
| Steps | V5は公式既定の23。V4.5以前はキットの初期値28。いずれも28以下 |
| １回の生成枚数 | １枚。複数枚の同時生成は使わない |
| 生成方法・追加機能 | テキストから生成。元画像・Precise Reference・Vibe Transfer等は既定で使わない |
| 実行前の確認 | 採用モデル・全設定を反映した消費表示が0 Anlasであること。V5はOpus利用上限の残量も確認 |

V5の既定が23ステップで、28ステップでは利用上限の消費が増えることは[公式の利用上限説明](https://journal.novelai.net/opus-usage-limit-explained-jp/)で確認した。同説明では、**V5のAnlas消費なし生成には時間とともに回復する利用上限があり、使い切るとAnlasでの生成になる**。V4.5以前にはこの利用上限は適用されない。したがって「Opusなら常に無制限・消費ゼロ」とは案内しない。

1. ユーザー指定の生成環境・モデルを保持し、Opusなら未指定のステップ数・枚数・追加機能を上表で決める。生成寸法は共通のページ設定に従う。採用寸法・ステップ数は無料条件と照合し、範囲内なら保持する。範囲外なら変更案を示し、指定を黙って上書きしたり、有料生成へ進んだりしない。変更への回答待ちや費用未確認で保留するのは、生成とその寸法に依存する配置だけ。企画・人物の呼び名・物語の整理など、未確定条件に依存しない作業は続けられることを案内し、必要なものを進める。
2. 採用した幅・高さを作品の `config/page-layout.json` の `generationCanvas` と実際の生成ツールの両方へ反映する。Steps・枚数・参照機能・費用条件はOPTIONの採用値と制作記録へ残し、生成ツールにも設定する。寸法JSONだけでステップ数や料金は制御されない。[枠配置と最終PNG](page-layout.md)は生成後の実寸から決める。
3. 毎回の実行前に、現在の全設定で0 Anlasを確認する。V5の利用上限が不足した場合はその生成を保留し、回復を待つ。確認できない場合も、費用確認のための試験生成はしない。モデル変更やAnlasを使う継続は、ユーザーの明示指示の範囲で行う。範囲が既に指示されていれば同じ許可を求め直さない。
4. 生成したPNGの実寸を確認し、採用寸法・Steps・枚数・モデル・0 Anlasの確認方法と日付を作品の通常の制作記録へ残す。実際に確認できなかった消費量を「実測0」と記録しない。API・外部クライアントではその環境の仕様と費用確認手段を調べ、UIと同じ無料条件が適用されると未確認のまま断定しない。

**追加料金に関する確認事実:** [Precise Reference](https://docs.novelai.net/en/image/precisereference/)は参照数に応じた追加Anlas、[Vibe Transfer](https://docs.novelai.net/en/image/vibetransfer/)はV4以降で初回・再エンコードや４件を超える参照に料金がある。参照画像やコマ枠を画像として入力する工程、Enhance・Upscale・Inpaint等の編集も、サイズとStepsだけで無料扱いにせず各機能の費用を確認する。参照機能を使わない場合は固定キャラ記述と生成後の目視で一貫性を確認する。

**未検証:** 利用者の契約状態、APIでの実消費、生成品質・文字の可読性。この調査ではログイン・生成・Anlas消費を伴う動作確認は行っていない。上表は公式条件に合わせた制作上の初期値で、品質を保証する推奨値ではない。仕様変更や表示との食い違いがあれば、その時点の公式条件を再確認する。

## 5. NovelAI APIの接続設計

公式画像APIの入口は `https://image.novelai.net`。公開スキーマで `POST /ai/generate-image`、画像ZIPまたはJSONの応答、`action`・`input`・`model`・`parameters` の構造を確認した。Persistent API tokenをAuthorizationヘッダーで使う設計が説明されている。APIには人の操作を起点とする生成と過大な自動負荷の禁止も記載されている。[公式画像APIスキーマ](https://image.novelai.net/docs/doc.json)（2026-09-12、公開仕様）

**接続実装（2026-09-21）:** 新規作品には `scripts/novelai_api.py` を同梱する。キーの自動読込、生成を伴わない契約照会、明示実行による１枚生成とPNG保存に対応する。[接続手順と動作確認プロンプト](novelai-api.md)を参照。生成要求例のモデルは未設定とし、選んだモデル名と機能について、その時点のスキーマを再確認する。参照画像UIの説明とAPIのフィールドを同一視しない。コードの実装と実APIでの確認は区別し、実動作の確認結果は作品側に記録する。

- キーは作品単位で管理し、共通テンプレート、ワークフローJSON、画像メタデータ、進捗ログに含めない。ログにはキーの有無や接続結果だけを記す。
- 要求の同一性を追えるリクエストIDと生成番号を記録し、タイムアウト時に結果不明のまま自動で多重送信しない。
- Opusでは先に[Anlasを消費しない生成条件](#novelai-opus)を適用し、費用条件を確認してから最初の１件の応答と保存を検証する。量産比較はローカルComfyUIを中心に行い、NovelAIの実行数・コストは作品ごとの実験計画に残す。

## 6. NovelAI → ComfyUIで絵柄を揃える工程

以下は**制作上の提案で、品質保証された実測済み手順ではない**。

1. **演出を先に固定する。** コマの役割、画角、表情、人物の位置、フキダシ用の余白を決める。
2. **NovelAIで元絵を作る。** 選んだモデル、固定キャラ記述、採用した参照条件を使い、顔・衣装・構図を先に確認する。Opusでは[Anlasを消費しない生成条件](#novelai-opus)を既定とし、参照機能の追加料金を分けて判断する。元PNGと設定を保存する。
3. **ComfyUIの処理を選ぶ。** 軽い絵柄調整には対応モデルでimg2img、姿勢や輪郭の保持が必要なら対応するControlNet、参照編集ならQwen-Image-Edit-2511を検討する。この分岐を別ワークフローとして扱う。
4. **強度を小さな範囲で比較する。** 通常のimg2imgではdenoiseを例として0.2／0.35／0.5で比較する。これらは試験値であり推奨成功値ではない。Qwenの参照編集へこの値をそのまま適用しない。
5. **前後比較する。** 絵柄が寄ったかに加え、顔、髪、衣装、左右、持ち物、表情、視線、フキダシ余白が壊れていないか確認する。
6. **局所修正してページで見る。** 問題箇所だけを修正し、隣り合うコマと最終掲載サイズで比較する。顔だけ過剰に精細になる等の不整合を戻す。
7. **採用版を固定する。** 元絵→編集→修正の対応、使ったワークフローと重みの版、採用理由を作品側に保存する。フィードバック記録を依頼された場合だけ、再現性のある条件を整理する。

通常のComfyUI img2imgは、参照画像を潜在表現へ変換し、denoiseで変更量を調整する例が公式にある。数値を強くするほど元画像との差が大きくなるという説明はこの処理に適用する。[ComfyUI img2img](https://docs.comfy.org/tutorials/basic/image-to-image)（2026-09-12、基本img2img例）

## 7. seedと再現性

同じseedは一貫性の保証にならない。NovelAIではプロンプト以外に解像度、生成枚数、参照画像なども一致させる必要があり、samplerによる非決定性も説明されている。NovelAIのseedをComfyUIへ移しても同じ絵には対応しない。[NovelAI Seed](https://docs.novelai.net/en/image/seed/)（2026-09-12、NovelAI画像生成）

Diffusers公式も、同一seedだけで完全再現は保証しないと説明している。乱数Generatorの状態は呼び出すと進むため、seedの記録と乱数状態の扱いを区別する。[Diffusers Reproducibility](https://huggingface.co/docs/diffusers/using-diffusers/reusing_seeds)（2026-09-12、Diffusers）

**制作上の運用:** ComfyUIの実行ごとのseed変化設定を確認し、再現テストでは固定する。モデルハッシュ、ノード版、ワークフローJSON、プロンプト、参照画像、sampler、scheduler、steps、guidance、denoise、解像度、batch、精度、LoRA強度をセットで記録する。同一マシンでの再現、別環境での近似再現、漫画としての採用可能性を分けて報告する。

## 8. 表情・ポーズの実験計画

以下の英語は**未検証の候補プロンプト**。公式に成功率が保証されたタグ一覧ではない。タグ型と自然文型は別条件で比較する。

| 目的 | タグ型候補 | 編集指示型候補 |
| --- | --- | --- |
| 小さな笑顔 | `gentle smile, closed mouth` | `Give the character a subtle closed-mouth smile. Keep the hairstyle and outfit unchanged.` |
| 明るい笑顔 | `open-mouth smile, raised cheeks` | `Show a joyful smile with raised cheeks and an open mouth. Preserve the character's identity.` |
| 驚き | `surprised, wide eyes, raised eyebrows, open mouth` | `Make the character look startled, with wide eyes, raised eyebrows, and a slightly open mouth.` |
| 身を引く驚き | `startled, leaning back, hands raised` | `Show the character recoiling in surprise, leaning backward with both hands raised near the chest.` |

プロンプトと別に、笑顔なら口角・頬・目、驚きなら眉・目・口・上体の何を必須とするかを決める。「驚き」が恐怖や喜びへ変わった失敗も残す。

### 第1段階: 24枚の小規模比較

実行可能なローカル経路を1つ選び、承認済みキャラ1名で行う。2表現（笑顔／驚き）×2指定方法（タグ／自然文）×3 seed×2画角（顔アップ／上半身）=24枚。seedは実験前に固定した3個を全条件で共用し、気に入った画像だけ選び直さない。各条件では指定方法以外のモデル・参照・設定を同一にする。

### 第2段階: 同一性と姿勢の両立

第1段階で使えた指定方法を固定し、2ポーズ（自然立ち／身を引く）×2参照方法（全身／顔を十分大きくした参照）×3 seed=12枚を比較する。画像編集モデルがタグに不向きでも、それ自体を条件付き結果として残す。複数モデルを比較する場合はモデルごとに同じ実験を独立に行う。

### 記録と判定

| 記録項目 | 内容 |
| --- | --- |
| 実験の同定 | experiment_id、run_id、日時、仮説、作品・キャラ・コマID、実行者 |
| 入力と設定 | 参照画像ID/ハッシュ、元画像ID、全文プロンプト、モデル/LoRA/ノード版、seed、解像度、batch、sampler等 |
| 量と失敗 | 予定数、送信数、正常生成数、エラー数、失敗画像、やり直し理由 |
| 表現成功 | 狙った感情／動作が読めるかを0=不可、1=曖昧、2=明確で採点 |
| 同一性・絵柄 | 各1～5点。1=別物、3=修正で使える、5=基準と一致。顔・衣装等の内訳を記録 |
| 構造・演出 | 手足の破綻、左右反転、持ち物、視線、余白、コマ内での読みやすさ |
| コスト | 秒/枚、初回ロード時間、ピークVRAM、必要ならRAM、手直し分/枚、API利用時の実コスト |
| 採否 | 採用/保留/不採用、理由、評価者、次に変える変数 |

**暫定合格条件:** 表現2点、同一性4点以上、衣装の重大な不一致と手足の重大破綻なし。合格数/正常生成数と、合格数/全試行数を両方示す。少数実験では例えば「2/3」と母数も明記し、一般的な成功率へ言い換えない。余裕があれば条件名を隠して2名が評価し、評価不一致を残す。自動の顔類似度だけで漫画の同一性を決めない。

**現在の実験状態:** 未実施。成功率・最適タグ・最適強度・生成速度・必要VRAMはいずれも未確定。

## 9. LoRAを作る場合の次段階

**制作上の提案:** 特定キャラを多数コマで使い、参照編集の修正工数が大きいと分かった時点で検討する。

1. 対象のベースモデル、学習器、その版を固定する。SDXL等の学習例をQwen用の動作保証にしない。
2. キャラ同一性を人が確認した画像だけを集める。角度・表情・衣装の偏り、誤った左右、重複を点検する。使用可能な素材の範囲も作品側に記録する。
3. 学習用と評価用を分離し、近い構図の画像が両方へ漏れないようにする。衣装や背景の説明をcaptionに含め、キャラと背景の結び付きを評価する。
4. rank、学習率、steps、画像数、解像度を記録し、小規模な条件から始める。推論の動作可否と学習の動作可否を別に測る。
5. 未学習のポーズ・表情・衣装で、参照のみの基準条件と比較する。キャラLoRAと絵柄LoRAを同時に導入する前に各々の効果を測る。
